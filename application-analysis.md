# SambaPOS V3 - Application Analysis

## 1. Application Overview

- **Purpose:** SambaPOS V3 is a touch-screen point-of-sale desktop application for restaurants and similar hospitality businesses. It manages tickets (bills), orders, payments, double-entry style accounts, inventory and cost, printing, reporting and rule-based automation, with optional multi-terminal synchronisation.
- **Technology stack:** C# on .NET Framework 4.0, WPF (XAML) with MVVM view models, MEF (`System.ComponentModel.Composition`) for composition and Prism (Microsoft.Practices.Prism, MefExtensions) for modules/regions, Entity Framework 4.4 (DbContext/Code First via `Samba.Persistance`), FluentMigrator for schema migrations, FluentValidation for view-model validation, Newtonsoft.Json for JSON-in-column storage, ValueInjecter for object copy, FluentScript (vendored in `src/Lib`) as the embedded expression/script engine, Stateless (vendored), ASP.NET Web API self-host for the API server, .NET Remoting (TCP, binary formatter) for the messaging server.
- **Framework version:** .NET Framework 4.0 (`TargetFrameworkVersion v4.0` in `Samba.Presentation`, `Samba.Domain`, `Samba.ApiServer` csproj files). Windows only (WPF, WinForms for servers, serial ports, Win32 raw printing).
- **Solution structure** (`src/SambaPos.sln`, 47 projects):
  - `Samba.Presentation` - WPF shell/executable (App, Bootstrapper, Shell, status views).
  - `Samba.Presentation.Common`, `.Controls`, `.Services`, `.ViewModels` - shared UI infrastructure, controls (touch buttons, virtual keyboard, popups), presentation-level services (TicketService, UserService, WorkPeriodService, InventoryService, TriggerService, TaskService, data seeding), a map controller view.
  - `Samba.Domain` - domain model (EF entities) and builders (`TicketBuilder`, `OrderBuilder`, `MenuItemBuilder`, `AccountTransactionTypeBuilder`, `TaxTemplateBuilder`).
  - `Samba.Infrastructure`, `Samba.Infrastructure.Data` - settings, messaging, cron, JSON helpers, base classes (`EntityClass`, `ValueClass`, `AbstractMap`), workspace abstractions.
  - `Samba.Persistance`, `Samba.Persistance.DBMigration` - DAOs, caching DAO, specifications, validators, FluentMigrator migrations 001-024.
  - `Samba.Services` - service layer: cache, automation engine (rules, conditions, expression engine), printing (formatters, print jobs, HTML-to-XAML conversion), account, entity, department, menu/price list, email, devices, settings, report, messaging client.
  - `Samba.Localization` - resource strings (21 supported language codes) and a localisation engine.
  - `Samba.Modules.*` (21 projects) - feature modules (see section 3).
  - `Samba.ApiServer` - WinForms host for an HTTP/JSON read-only API.
  - `Samba.MessagingServer`, `Samba.MessagingServer.WindowsService`, `Samba.MessagingServerServiceTool` - terminal-synchronisation server (WinForms app, Windows service, service control tool).

- **Authentication mechanism:** PIN-only login. A user is identified by a 4-20 character PIN (`User.PinCode`, unique across users, stored as plain text). The login pad publishes the PIN; `UserService.LoginUser` checks `UserDao.GetIsUserExists(pin)` and loads the user with role and permissions. No password, lockout, or hashing. The login status enum has an unused `Suspended` value. After login the `UserLoggedIn` event is raised (UI topic and automation rule event). The terminal flag `AutoLogout` logs the user out after each ticket close. If only the default user with PIN 1234 exists on a CE/TX database, the login view shows an admin-password hint. The API server uses the same PIN to issue a token.
- **Authorisation approach:** programmatic permission checks in code (`IUserService.IsUserPermittedFor`), UI visibility/enablement through view-model `CanExecute`, and data-driven visibility through **mappings** (`AbstractMap`: Terminal, Department, UserRole, TicketType; 0 = any) on automation commands, rules, payment types, change payment types, calculation selectors, entity screens, order tag groups (plus product group/product), ticket tag groups, account transaction document types, print-job maps. Void/gift availability is controlled only by automation-command mappings (there is no void permission).

## 4. Workflows and Behaviours

#### Application start-up
- **Type:** system/background
- **Trigger:** launching Samba.Presentation.exe.
- **Steps:**
  1. `App.OnStartup` runs `Bootstrapper` (Prism/MEF) - composes `Samba.Persistance`, `Samba.Modules*`, `Samba.Presentation*`, `Samba.Services*` assemblies from the executable folder (Bootstrapper.cs).
  2. A named mutex enforces single instance (broadcasts a window message to the running instance) unless `AllowMultipleClients`.
  3. Language set from `LocalSettings.CurrentLanguage`; splash screen shown; messaging listener registered; messaging client started if `StartMessagingClient`.
  4. `DataCreationService.CreateData()` creates default currencies and, on an empty database, seeds default data (see section 9 notes). Failures prompt for a corrected connection string and exit.
  5. Status views registered; `TriggerService.UpdateCronObjects()` starts cron triggers; collection sort file loaded; caller-ID device initialised if configured; shell shown; `ShellInitialized` event published.
  6. `ApplicationStarted` rule event is raised. On exit the messaging client and triggers are stopped.
- **State transitions:** none (application lifecycle).
- **Source files:** Samba.Presentation/App.xaml.cs, Bootstrapper.cs, Shell.xaml.cs; Samba.Presentation.Services/Common/DataGeneration/DataCreationService.cs.

#### Login and logout
- **Type:** user-facing
- **Trigger:** PIN entered on the login pad.
- **Steps:**
  1. `UserService.LoginUser(pin)` verifies the PIN exists (LoginStatus CanLogin / PinNotFound) and loads user + role + permissions.
  2. Current user stored; `CURRENTUSER` local setting updated; caches reset.
  3. `UserLoggedIn` UI event and rule event raised; the department selector sets the current department from the role's default department; navigation screen is activated.
  4. Logout (button, or automatically if terminal `AutoLogout` after a ticket closes): rule event `UserLoggedOut`, current user reset, caches reset. Logout is blocked while the application is locked (ticket open).
- **State transitions:** Nobody -> logged-in user -> Nobody.
- **Source files:** Samba.Presentation.Services/Implementations/UserModule/UserService.cs; Samba.Modules.LoginModule/*; Samba.Modules.UserModule/LoggedInUserViewModel.cs; Samba.Modules.DepartmentModule/DepartmentSelectorViewModel.cs.

#### Start and end work period
- **Type:** user-facing
- **Trigger:** user with OpenWorkPeriods opens Day Operations.
- **Steps:**
  1. Start: allowed when no period exists or the latest period is closed (`StartDate != EndDate`). `WorkPeriodDao.StartWorkPeriod` is a no-op when the latest period is still open. Inside a transaction, all `IWorkPeriodProcessor`s run (`InventoryWorkperiodProcessor.DoWorkPeriodStart` recalculates final costs of the previous period if recipes exist). `WorkPeriodStarts` rule event and feedback follow.
  2. End: allowed only on the WorkPeriods screen with zero open tickets (`GetOpenTicketCount` counts all non-closed tickets in the database), the period older than one minute, and the period open. `BeforeWorkPeriodEnds` rule event, then `StopWorkPeriod` sets `EndDate`/`EndDescription` and runs processors (`DoWorkPeriodEnd` creates and saves the periodic consumption record when recipes exist, removing zero rows), then `WorkPeriodEnds` rule event.
  3. Failures are logged and rolled back with a generic error message.
- **State transitions:** WorkPeriod open (`StartDate == EndDate`) -> closed (`EndDate` set).
- **Source files:** Samba.Modules.WorkperiodModule/WorkPeriodsViewModel.cs; Samba.Presentation.Services/Implementations/WorkPeriodModule/WorkPeriodService.cs; Samba.Persistance/Implementations/WorkPeriodDao.cs; InventoryService.cs.

#### Create / open ticket and take orders
- **Type:** user-facing
- **Trigger:** selecting an entity on an entity screen, pressing Add Ticket, selecting an open ticket, scanning a barcode, or an automation action.
- **Steps:**
  1. `PosViewModel.DisplayTickets`: if a ticket is selected, no ticket entity screens exist, or the department creation method is "create ticket", go straight to the ticket screen; otherwise the entity selector is shown.
  2. On entity selection (`EntitySelected` rule event fires first): with no selected ticket, look up open tickets of the entity; none -> optionally ask ticket type (when the entity screen has AskTicketType and more than one ticket type exists) then `OpenTicket(0)` and assign entity; one -> open it; several -> show a ticket list.
  3. `TicketService.OpenTicket(0)` builds a new ticket from the current ticket type and department (`TicketBuilder`), sets exchange rate from the sale transaction type's default target account currency, pre-applies calculation selectors without a button header, and raises `TicketCreated`. Opening an existing ticket raises `TicketOpened`.
  4. If the ticket has no orders, mandatory entity assignments (`AskBeforeCreatingTicket`) and ticket tags (`AskBeforeCreatingTicket`) are requested before the menu is shown.
  5. Selecting a menu item (or typing `qty x barcode`, or a weight-barcode) calls `TicketService.AddOrder`: rejects if ticket is locked without `AddItemsToLockedTickets`, if closed, or if the portion is missing; applies department price tag, product timer, tax templates, quantity (quantities > 9 are divided by the portion multiplier), optional order states from the menu item, recalculates, raises `OrderAdded`. The menu item may also pre-apply order tags, order states and an automation command; AutoSelect opens the order for tagging.
  6. Orders can be tagged (order tag groups with min/max/free tagging), have quantity changed (unlocked orders), price changed (permission), cancelled (new orders only), moved, or have automation commands executed.
- **State transitions:** Ticket created (Id 0, unsaved) -> saved on first close with orders -> locked/closed later. Orders unsaved (Id 0) -> saved/locked.
- **Source files:** PosViewModel.cs, TicketViewModel.cs, TicketOrdersViewModel.cs, MenuItemSelectorViewModel.cs, TicketService.cs, TicketBuilder.cs, OrderBuilder.cs.

#### Close (submit) ticket
- **Type:** user-facing / system
- **Trigger:** Close command (default automation command "Close"), leaving the ticket, or an action `CloseActiveTicket`.
- **Steps:**
  1. `PosViewModel.CloseTicket`: refuses if `!CanCloseTicket()` (remaining != 0, no entity and orders exist) unless a defined ticket tag is set; when remaining is zero it checks for zero-priced calculable orders and for missing force-value ticket tags (see BR-011, BR-012).
  2. `TicketService.CloseTicket`: concurrency check (`CheckConcurrency`); if not changed and not closed: recalculate; raise `BeforeTicketClosing` (default rule marks Paid and closes when remaining = 0); if orders exist: assign order numbers from the OrderNumerator and merge identical new orders; first save assigns ticket number from TicketNumerator and saves; raise `TicketClosing` (default rule prints new orders to the kitchen and sets Unpaid / Submitted states); lock orders (and ticket if a lock was requested); remove zero-amount transactions of closed tickets; save.
  3. `EntityUpdated` is raised for each ticket entity with the number of open tickets (default rule: 0 open tickets -> entity state Available).
  4. A `TICKET_REFRESH` message is broadcast to other terminals; terminal may auto-logout; the POS view is re-activated.
- **State transitions:** Ticket status states per default rules: New -> New Orders -> Unpaid -> Locked (after bill) -> Paid (closed). `IsClosed`, `IsLocked` flags.
- **Source files:** PosViewModel.cs, TicketService.cs, TicketDao.cs, RuleGenerator.cs.

#### Order operations: cancel, gift, void, move, split
- **Type:** user-facing
- **Trigger:** buttons on the ticket orders panel.
- **Steps:**
  1. Cancel (`CancelItemCommand`): only unsaved (Id 0), unlocked orders; raises `OrderCancelled` and removes them.
  2. Gift/Void/Cancel Gift/Cancel Void are default automation commands (display on orders). Each raises `AutomationCommandExecuted` per selected order; default rules call UpdateOrder + UpdateOrderState to set flags and `GStatus` state (Gift: DecreaseInventory = true, CalculatePrice = false; Void: DecreaseInventory = false, CalculatePrice = false; cancels restore both true and clear state; Cancel Void also sets Status = Submitted).
  3. Move (`MoveOrdersCommand`): needs MoveOrders/MoveUnlockedOrders permission, unlocked ticket, saved orders, and selected value not exceeding remaining amount. Partially selected quantities are split via `Ticket.ExtractSelectedOrders` (clones order, reduces original quantity). `TicketService.MoveOrders` raises `TicketMoving`, `OrderMoving`, clones orders, closes the source ticket, opens the target (new ticket if id 0), adds orders, raises `OrderMoved` and `TicketMoved`, saves (default rule resets status to New Orders).
  4. Merge (`MergeTickets`) requires permission; fails if any ticket has calculations or entities of the same type differ; clones orders, payments, change payments, tags, entities and logs into one new ticket, closes old ones (data removed), raises `TicketsMerged`.
- **Source files:** TicketService.cs, TicketViewModel.cs, TicketListViewModel.cs, RuleGenerator.cs, Ticket.cs.

#### Payment and settlement
- **Type:** user-facing
- **Trigger:** Settle command (default rule -> `DisplayPaymentScreen`) or `PayTicket` action.
- **Steps:**
  1. `PaymentEditorViewModel.Prepare` loads the ticket, number pad and order selector.
  2. Optional: select orders (partial pay), foreign currency (recomputes selector prices by exchange rate; optional rounding adds the difference to the cheapest remaining order selector), calculation selector buttons (discount/round), account mode.
  3. Pressing a payment type: allowed if the ticket is open, tendered value non-zero, remaining amount non-zero and either the payment type has a fixed account or one ticket entity can take the transaction (`CanMakeAccountTransaction`, account working rules). Amount tolerance of 0.01 snaps due/tendered to remaining.
  4. Tendered above due: change is returned; with a foreign currency and several change payment types the user chooses one; otherwise `ChangePayment` posts to the change account.
  5. `TicketService.AddPayment` creates an account transaction (source/target per payment transaction type) and `Payment`; raises `PaymentProcessed`; remaining amount recomputed.
  6. Account mode: if payment exceeds the ticket remainder, the surplus up to the active account's balance is posted as an account transaction (`AccountTransactionAddedToTicket`).
  7. If remaining reaches 0 (and no change prompt) the payment screen closes; the close flow raises `BeforeTicketClosing` (default rule sets Paid and `MarkTicketAsClosed`) so the ticket becomes closed.
  8. If negative remaining arises (discount too large), all button discounts are removed ("All discounts removed").
- **State transitions:** Unpaid/Locked -> Paid; `Ticket.IsClosed` true and PaidItems cleared.
- **Source files:** PaymentEditor.cs, PaymentEditorViewModel.cs, OrderSelector.cs, ForeignCurrencyButtonsViewModel.cs, TicketService.cs, Ticket.cs.

#### Print bill
- **Type:** user-facing
- **Trigger:** default automation command "Print Bill" (ticket and payment screens; enabled in states New Orders, Unpaid, IsClosed).
- **Steps:** Default rule actions in order: ExecutePrintJob "Print Bill"; LockTicket (request); UpdateEntityState Status = Bill Requested; UpdateTicketState Status = Locked; CloseActiveTicket. The ticket lock takes effect when the ticket is closed.
- **Source files:** RuleGenerator.cs, ExecutePrintJob.cs, LockTicket.cs, CloseActiveTicket.cs.

#### Rule engine execution (automation)
- **Type:** system/background
- **Trigger:** any `ApplicationState.NotifyEvent(eventName, data)` call.
- **Steps:**
  1. `NotificationService.NotifyEvent` -> `RuleExecutor.SelectFor(event).WithTerminalId/DepartmentId/UserRoleId/TicketTypeId`.
  2. `CacheService.GetAppRules` selects rules for the event whose `AppRuleMap` rows match the context (0 or equal for each of terminal, department, user role, ticket type) ordered by `SortOrder`.
  3. `ConditionChecker.Satisfies`: custom constraint list (`RuleConstraintValue` JSON, match mode Match Any / Match All / Not Any / Not All / default grouped), legacy `EventConstraints` (`name;op;value` joined by `#`), and the rule's script constraint. Constraint operations include Equal, NotEquals, Greater, Less, IsNull, IsNotNull, Contains, Starts, Ends, LengthEquals, Matches, NotMatches, MatchesMod10, After, Before. Values are pre-processed (settings, `[:param]`, model data, expressions).
  4. For each satisfied rule, its `ActionContainer`s (by sort order, each with an optional custom constraint script) are turned into `ActionData` (action definition cloned, parameters merged: container `ParameterValues` `name=value#name=value` override action `Parameter`, placeholders replaced) and published as `ExecuteEvent`; the `AutomationModule` handler dispatches to the registered `IActionType`.
  5. Message sub-flow: `SendMessage` action broadcasts `ActionMessage`; receivers' `MessageReceived` rules run.
- **Source files:** Samba.Services/Implementations/AutomationModule/*, RuleActionTypeRegistry.cs, Samba.Presentation.Common/Services/ApplicationState.cs, Samba.Modules.AutomationModule/AutomationModule.cs.

#### Trigger (scheduled automation)
- **Type:** system/background
- **Trigger:** cron-style expression of a `Trigger` row (parsed by `CronSchedule`).
- **Steps:** `TriggerService` creates one `CronObject` per trigger at start-up and when triggers change; on firing it updates `LastTrigger`, and unless the Management screen is active raises `TriggerExecuted` with `TriggerName`; a trigger that no longer exists stops itself.
- **Source files:** TriggerService.cs, Samba.Infrastructure/Cron/*, TriggerListViewModel.cs.

#### Multi-terminal synchronisation
- **Type:** system/background
- **Trigger:** ticket close, widget refresh, broadcast action.
- **Steps:** Terminals attach to the .NET Remoting `MessagingServerObject` ("ChatServer"); `SendMessage` posts `key:<command>data` strings which the server notifies to all attached clients; clients poll their queue every second and publish `MessageReceivedEvent`; handlers: `TICKET_REFRESH` and `WIDGET_REFRESH` for entity dashboards/ticket lister, and `ActionMessage` -> `MessageReceived` rule event. Connection loss triggers reconnect on the next send.
- **Source files:** Samba.Services/Implementations/Messaging/MessagingService.cs, Samba.Infrastructure/Messaging/*, Samba.Presentation.Common/MessageListener.cs, MessageProcessor.cs.

#### Print job execution
- **Type:** system/background
- **Trigger:** `ExecutePrintJob` action, report print, account document print.
- **Steps:** `TicketPrintTaskBuilder` selects orders (all / last N lines by printer page height / last paid orders / separated by quantity), groups orders per printer map using product group code then product id precedence, formats each task with `TicketFormatter` using the printer template, skips tasks whose printer has no share name, whose template is missing, or (non-custom printers) which have no orders while the template contains `{ORDERS}`; `TicketPrinter` queues tasks on `AsyncPrintTask` (normal/high priority thread). Printer type selects `PrintJobFactory` implementation: slip/ticket (0), text (1), HTML (2), port (3), demo (4), Windows (5), custom (6), raw (7).
- **Source files:** TicketPrintTaskBuilder.cs, TicketPrinter.cs, PrintJobFactory.cs, AsyncPrintTask.cs, PrintJobs/*.

#### End-of-day inventory and cost
- **Type:** system/background (with user stock-count step)
- **Trigger:** work period end; manual edit of the end-of-day record.
- **Steps:** see BR-031 to BR-034. On end: per warehouse create `PeriodicConsumptionItem`s (in stock from previous physical or predicted stock, purchases/removals from inventory transactions, consumption from sales x recipes), create cost items per sold portion, store. On next start: recompute the previous period's final cost after any physical inventory counts.
- **Source files:** InventoryService.cs, PeriodicConsumption*.cs, WarehouseConsumption.cs, InventoryDao.cs, PeriodicConsumptionView(Model).

#### Account document creation (e.g. customer payment)
- **Type:** user-facing
- **Trigger:** Accounts screen > select account > document-type button; or batch creator; or rule action.
- **Steps:** default amount and description built from templates (`[Balance]`, `[BalanceEx]`, `[:field]`, `[MONTH]`, `[NEXT MONTH]`, `[WEEK]`, `[NEXT WEEK]`, `[YEAR]`, `[ACCOUNT NAME]`); the account chooser lists accounts by filter (all / balanced only / mapped); `AccountTransactionDocumentType.CreateDocument` builds one transaction per transaction type with the master account and chosen counter accounts; exchange rate from currency or fixed template; saved; `AccountTransactionDocumentCreated` raised; optional print by printer template.
- **Source files:** AccountService.cs, DocumentCreatorViewModel.cs, BatchDocumentCreatorViewModel.cs, AccountTransactionDocumentType.cs.

#### Caller-ID popup
- **Type:** system/background; **Trigger:** serial data from device. **Steps:** parse number -> trim characters -> popup on UI thread -> search customers by phone -> single match shows customer name else raw number -> click opens entity selection -> rule event `DeviceEventGenerated`. **Source:** CidMonitor project.

#### Product timer pricing
- **Type:** user-facing; **Trigger:** order of a product mapped to a `ProductTimer`. **Steps:** order stores a `ProductTimerValue` (start = end = active); price = unit price / PriceDuration x elapsed time (min, hour or day) with minimum time and rounding up to `TimeRounding`; stopping sets `End`. A ticket with active timers cannot be marked closed. Source: ProductTimerValue.cs, Ticket.cs (`HasActiveTimers`, `Close`), StopActiveTimers.cs.

## 9. Cross-Reference: Application to Database

#### 9.1 Data Access Patterns

- **Primary data access approach:** Entity Framework 4.4 `DbContext` (Code First, `Samba.Persistance/Data/DataContext.cs`, `CommonDbContext`) wrapped by a workspace abstraction (`IWorkspace`, `WorkspaceFactory.Create()`), a static `Dao` helper (Query/Single/Select/Exists/Count/Save with expression predicates), a `CachedDao` for ICacheable entities (Ticket, Entity, Task, PeriodicConsumption, EntityScreenItem) with last-update-time optimistic concurrency, and per-aggregate DAO classes (`TicketDao`, `AccountDao`, `EntityDao`, `InventoryDao`, `MenuDao`, `PriceListDao`, `PrinterDao`, `SettingDao`, `TaskDao`, `UserDao`, `WorkPeriodDao`, `AutomationDao`, `CacheDao`) exported through MEF interfaces. Specification pattern for queries; FluentValidation-style save/delete validators registered in `ValidatorRegistry`. Schema evolves via FluentMigrator `Migration_001`-`Migration_024`; the database version is checked at start-up. Many child collections are stored as JSON strings in a column of the parent (see section 6). Note: no stored procedures are called from the application code.

## 10. Known Deficiencies, Dead Code, Security Observations and Differences from the Knowledge Base

Items are factual observations from the code; they are not recommendations.

**Security**
- PINs are stored and compared in plain text (`UserDao.GetUserByPinCode`); no lockout, rate limiting or audit of failed logins. `LoginStatus.Suspended` is defined but never produced.
- Default administrator PIN is 1234 and the login screen displays a hint while it is unchanged on CE/TX databases.
- The API server issues tokens from `GET api/getToken/{pin}` (PIN in the URL path), over plain HTTP, with tokens kept as XML files in `%ProgramData%\Ozgu Tech\SambaPOS3\token`; there is no role-based authorisation or TLS. Responses serialise whole domain objects (tickets with payments/entities, user role including permissions). `Token` lookup trusts a user supplied GUID string as part of a file name (`GetFilename`) without validating its format (path characters not checked).
- Messaging uses .NET Remoting with a binary formatter at `TypeFilterLevel.Full` and no authentication; any host that can reach the port can attach and broadcast, including `ActionMessage` that triggers rules on all terminals.
- `StartProcess`, `AddLineToTextFile`, `SendEmail`, `ExecuteScript` and `SetCurrentTerminal` actions let anyone who can edit rules execute arbitrary programs/scripts or change identity. SMTP credentials are action parameters stored in the database. The email service can globally disable certificate validation (`ServicePointManager.ServerCertificateValidationCallback = ... true`).
- The error report dialog can upload a report to `http://reports.sambapos.com` over HTTP.
- Permissions `ChangeItemPrice` (checked in `TicketViewModel.CanChangePrice`) is never registered through `PermissionRegistry`, so the role editor cannot grant it; non-admin users can only change the price of zero-priced orders. `RemoveTicketTag` and `ChangeExtraProperty` are registered but no enforcement was found. `Void` has no permission (restricted only by command mappings).

**Defects and risky logic**
- `AddOrder` action: `order.UpdatePrice(...)` and flag assignments run before the `order != null` check although `TicketService.AddOrder` returns null for locked/closed tickets or missing portions (NullReferenceException risk) (`AddOrder.cs`).
- `AccountTransactionDocumentType.CreateDocument` reassigns `amount = amount * amountRate` inside the transaction loop, so with several transaction types in foreign currency the amount compounds (`AccountTransactionDocumentType.cs`).
- Account working rule semantics are inconsistent: `AccountType.WorkingRule` comment says "1 disallow debit, 2 disallow credit" while `CanMakeAccountTransaction` implements 1 as "disallow credit" (negative balance) and 2 as a credit-limit check.
- `ExpressionEngine`/accessors keep the current Ticket/Order/Entity/Data as static fields (`TicketAccessor.Model` etc.) and one shared interpreter - scripts are not thread safe; `Between` always returns `int.MaxValue`.
- `AccountReportViewModelBase.GetBalancedAccounts` returns an empty list: Liability, Receivable and Internal Accounts reports never show data.
- `CometDevice`: the opened `SerialPort` is a local variable while `_port` (used in `DataReceived` and `DoFinalize`) is never assigned in the code read - receiving data/finalising would raise NullReferenceException.
- `CustomPrinterJob` has a `NotImplementedException` member (`PrintJobs/CustomPrinterJob.cs`); `AccountGroupsConverter` and several converters throw `NotImplementedException` for `ConvertBack`.
- `ProgramSettings.AutoRoundDiscount` exists but is not consumed anywhere; `QuantitySeparators`/weight barcode settings are consumed only by the POS numerator.
- `OrderMerger.OldMerge` is dead code (only `NewMerge` is called); `Ticket.GetPaidItems`/`PaidItem` matching uses `menuItemId_price` keys, so orders of the same product at different prices are handled but orders with tags are not distinguished.
- `Order.GetPrice()` adds all order tag prices while `GetVisiblePrice()` adds only tags with `AddTagPriceToOrderPrice`; reports and inventory use mixed accessors, which can make displayed and billed totals differ in presentation.
- `TicketService.MergeTickets` closes the source tickets after `RemoveData()` without checking each close result.
- The Work Period "open tickets" check counts every non-closed ticket in the database, regardless of department/terminal, and the end-description input in the UI is bound to the start description (per the knowledge base; code binds `EndDescription` property but the view binding was not verified here).
- Inventory consumption (`InventoryDao.GetOrdersFromRecipes`) loads all tickets after the work period start with orders into memory and filters in LINQ-to-Objects (scalability concern). `Dao.Query<Ticket>` is also used for the CSV export and reports.
- `LocalSettings.Decimals` is hard-coded to 2 although currencies and rounding are configurable; `TicketService` messages "Can't merge tickets" are hard-coded English; several Turkish identifiers/comments/table keys remain in code (`GelirlerTablosu`, `Maliyet`, comments in Order.cs, Calculation.cs).
- Class and property typos retained in the model and mapped to the database: `ProdcutTimerMap`, `ProdcutTimerMap.cs`, `Productimers` DbSet, `PaymentType..cs`, `OrderTagGroup.AddOrderTag`, `UdpateEntityData`, `AccountScreenAutmationCommandMap`, `AutmationCommandMaps`, `AddPChangeaymentTemplateMap`, `OrdersByQuanity`.
- Debug-only checks (`Debug.Assert`) guard important invariants (ticket numbers, order numbers, user login state); in release builds they do nothing.
- Hard-coded entity type id: `EntitiesController.GetAllEntities` always queries entity type id `2`.
- The default customer entity type is located by the localised name "Customers" (`AbstractCidDevice`), so renaming it or changing language breaks caller-ID lookup. Account-document `[Balance]` default amount is also matched using a localised resource string.

**Dead or unreferenced features / not present in V3 (consistent with knowledge base section 9)**
- No V2 style hard-coded Gift/Void reasons, service templates, "TopItems" sort, user passwords, separate Terminal application; no automatic backup, re-open paid ticket, order tag prefixes, inventory semi-products. Payment type "display under ticket" was removed (Migration_018).
- `Suspended` login status, `ChangePayment` UI for non-foreign currency flows (change types are offered only when a foreign currency is selected), `IMessageListener` Reconnect without back-off, and `PowerBroadcastStatus` handlers in the Windows service (all empty) are placeholders.
- `Samba.Presentation.ViewModels` contains only a small map controller; `Samba.Modules.MarketModule` is a thin browser wrapper to an external site.

**Differences from the supporting knowledge base (code is authoritative)**
- The knowledge base lists messaging server default as unspecified; the code defaults the settings object to port 8080, the Windows service to 8383.
- Knowledge base says account reports "return no data"; confirmed (`GetBalancedAccounts`).
- Knowledge base mentions `AutoRoundDiscount`-like behaviour only through foreign-currency rounding; the program setting itself is unused.
- Permission list in the knowledge base is generic; the exact registered permission names are in section 2.
- Quantity above 9 divided by portion multiplier and the "zero-priced product" close rule are not described in the knowledge base.
